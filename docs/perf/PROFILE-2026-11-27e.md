# Effect-runtime attribution (2026-11-27e), investigation only, no src change

Profile: the 2026-11-27d windowed profile (400 conversations, 7346 busy samples, 33.5 ms CPU per conversation).
Tool added: `scripts/perf/cpuprofile-effect-owners.ts` (`--mode=self` attributes effect-runtime leaf samples to the nearest repo frame; `--mode=names` and `--mode=owners` give inclusive counts). Per conversation = samples / 400.

## Effect-runtime leaf samples
- 7.28 of 18.2 busy samples per conversation (40%) have an effect-runtime leaf.
- 3.95 of those (54%) have no repo frame above them: Scheduler drain (`runTasks`, `afterScheduled`) and `runLoop` resuming async continuations. This is runtime cost, not attributable to a repo function.
- 1.70 sit under `Integration.list` (integration.ts:711), 23% of effect leaves, about 9% of all busy samples.
- 0.38 under `Store.all` credentials (store.ts:149); 0.08 projector encodeStored; all others under 0.1.

## Categories (a) to (d)
- (a) Fibers forked: `forkUnsafe` 2.97 per conversation inclusive (16%). Fork count not directly measured; each fork carries a Scheduler hop.
- (b) Spans, annotate, logs: no span, trace, log, annotate or metric frame appears among the top 80 Effect frame names. Not proven absent beyond that list.
- (c) Context lookups: `Context.lookup` 0.24 per conversation (1.3%). SQL builder frames (`_prepare`, `get`, `all`, `from`, `execute`) about 2.6 per conversation inclusive, about 0.016 samples per statement across 163 statements: per-statement Effect overhead is small.
- (d) Stream: no Stream frame among the top 80; SSE deltas are timer-batched (see LOG), so per-token Effect work is not a visible share.

## Conclusion
The 45% is mostly structural runtime (scheduler drain and fiber resumes, 3.95 of 7.28 leaf samples with no repo owner). Repo-attributable Effect work is dominated by `Integration.list`, which runs twice per conversation via `Provider.snapshot` (provider.ts:469). It is the only single change above 5% of busy samples. Expected saving if removed: about 2.8 of 18.2 samples, roughly 15% of CPU (about 5 ms per conversation).

## Decision: no src change
A skip of `integrations.list()` needs credential writes from other processes to bump `integrations.revision()`, which is not proven (see LOG, 2026-11-27 provider-call attribution). Not provably identical, so not implemented. Next: a per-turn snapshot memo (turn-scoped FiberRef) or a cross-process credential version counter, then re-measure with the same 400-conversation window.
