## Findings

Ranked by expected effect on a short-lived `serve --stdio --port 0` boot plus the first prompt, versus safety of the fix. Paths are relative to the repository root. Source was not edited. A `run --standalone` spawns the same child as `Standalone.start` (`packages/cli/src/services/standalone.ts:18-39`): `serve --stdio --port 0`, so the findings below apply to both entry points.

Location-only boot work such as config discovery, skill and instruction scans, and watcher setup is unit 31's scope. This unit reports costs that remain per standalone process or that unit 31 did not cover.

### 1. Automation claims and releases the shared SQLite writer on every boot, even with no active or pending automation

- `packages/server/src/process.ts:134-135` forks `Automation.Service.run` for every server process, including `--stdio`.
- `packages/core/src/automation.ts:1017-1036`: on the first loop, `hasActiveRows()` is false, but `leadership === "unchecked"`, so the code still runs `claimLeader` at `:827-832`. That executes the prepared `INSERT ... ON CONFLICT ... KV` at `:800-817`; the `!active` branch at `:1034-1037` then calls `releaseLeader`, whose `DELETE` is at `:818-823` and `:834-838`.
- Cost scenario: every standalone opens the same database as the long-lived service and performs one KV write plus one KV delete before doing any prompt work. With `busy_timeout = 5000` (`packages/core/src/database/database.ts:46`), the burst of `run --standalone` processes already observed in `docs/perf-loop/LOG.md` (cycle 9) makes these writes contend for the single SQLite writer even though the worker will never run an automation.
- Minimal safe fix: before claiming, test for pending work as well as active rows. The existing `rewakeQuery` (`automation.ts:772-776`) already joins `AutomationTable.last_message_id` to `SessionInboxTable.id`; add a `LIMIT 1` variant and go straight to `dormant` when both `hasActiveRows()` and that pending check are empty. Active schedules and the finished-automation-with-pending-prompt recovery keep exactly their current behaviour.
- Risk: low. A row inserted between the check and the dormant decision is not seen until the next doorbell or restart, but the same race already exists between `hasActiveRows()` and `claimLeader`. Tests that assert a startup leader claim need a pending or active row in their fixture.

### 2. ModelsDev starts an HTTPS catalog refresh on every standalone process boot

- `packages/core/src/models-dev.ts:932-936` forks `refresh()` immediately in the layer, then repeats it every five minutes. `fetch` is on by default: `packages/cli/src/server-process.ts:124-128` passes `fetch: !OPENCODE_DISABLE_MODELS_FETCH`, and the server route graph configures it at `packages/server/src/routes.ts:168`. The node is a global node (`models-dev.ts:941-949`) pulled in through the plugin requirements (`packages/core/src/plugin/internal.ts:234`), so a long-lived service fetches once per process; every `run --standalone` is a new process and fetches again.
- Cost scenario: every one-prompt `run --standalone` starts a fresh process and therefore a fresh global `ModelsDev` layer. It issues one models.dev request at boot even when the on-disk catalog is fresh and even though the prompt would be served correctly from the bundled snapshot or KV cache. A pool of 30 workers makes 30 concurrent catalog requests and cache-metadata writes for the same result.
- Minimal safe fix: do not run the first refresh during layer construction. Start the existing periodic loop after a short delay (or after server readiness) so a short-lived process can finish its prompt on the cached/bundled catalog, while a long-lived service still refreshes on the same interval. `populate` already fetches on an actual cache miss, so the on-demand path keeps correctness.
- Risk: low to medium. A fresh install can show bundled model metadata for the delay window instead of immediately fetching newer data; tests using `TestClock` to assert an immediate refresh after layer build need to advance to the new start time. Do not remove the periodic refresh for long-lived servers such as the desktop stdio sidecar.

### 3. Database bootstrap and the V1 migration probe run on every boot with no version fast path

- `packages/core/src/database/database.ts:52` calls `DatabaseMigration.apply` for every database layer build. `packages/core/src/database/migration.ts:28-32` reads `sqlite_master`, then `applyOnly` unconditionally issues `CREATE TABLE IF NOT EXISTS migration` (`migration.ts:57-64`) and reads every migration ID into a set. Only after that does it skip the already-applied migrations.
- `packages/core/src/database/v1-migration.bun.ts:512-527` forks `run()` on every boot; `run` reads the migration-state KV row (`:548-550`) and then probes `sqlite_master` for the legacy `session` table (`hasLegacySessions`, `:1229-1234`). For a V2-only database both steps are pure boot probes.
- Cost scenario: three or four extra statements per standalone, including a DDL statement, on a database where nothing has changed. Under the same burst, the DDL can wait behind another process's write lock for up to five seconds before the worker can even open its Location; the V1 probe then does a second redundant schema read.
- `packages/core/src/database/database.ts:43-50` also sets four tuning pragmas and `foreign_keys` on each new connection. Only `journal_mode = WAL` can need a write lock; reading `PRAGMA journal_mode` first and setting it only when it differs removes that potential lock on an already-WAL file. `synchronous`, `busy_timeout`, `cache_size` and `foreign_keys` are per-connection and cheap, and this checkout issues no checkpoint work at boot.
- Minimal safe fix: store a bootstrap generation in `PRAGMA user_version` (a constant bumped whenever `migrations` changes) after a successful `apply`/`applyOnly`, and read it first. When it matches, skip the `CREATE TABLE`, the migration-ID read and the V1 fork. For the V1 path specifically, reuse the table list already read by `apply` or cache a "no legacy session table" marker so the second `sqlite_master` lookup is not needed.
- Risk: medium. A forgotten generation bump would leave a new migration unapplied; a half-applied migration must not write the marker, so set it only after the transaction commits and fall back to the full path on any mismatch. A manually edited database also falls back. Add a test that runs the bootstrap twice and asserts the second run issues no DDL.

### 4. Plugin activation synchronously checks every package plugin for updates

- `packages/core/src/plugin/supervisor.ts:195-228`: activation awaits `updates.check(target)` for every resolved package plugin at `:201-204` before applying the settled generation and releasing readiness. `packages/core/src/plugin/update.ts:42-62` implements `check` with `npm.check(target)`, which reaches the npm registry or a Git remote.
- Cost scenario: for each configured package plugin, the first Location boot waits on a network/child-process check before the registry is considered activated. A one-prompt run never needs to know whether a newer plugin version exists; it only needs the installed one to load. With several plugins this can add hundreds of milliseconds and child processes to every standalone boot.
- Minimal safe fix: move the initial `updates.check` fan-out out of the activation path. Either run it on the existing 24-hour interval stream (`plugin/update.ts:10`, `:39-43`) or fork it after activation with a short delay, keeping the same `outdated`/`updating` events and the existing auto-update logic.
- Risk: low. Automatic plugin updates and "update available" notifications arrive one interval or delay later. Plugins that are only installed, not checked, keep loading from the installed version. Tests that assert the first `check` happens during activation need adjustment.

### 5. Project archive sweep runs immediately on every server boot

- `packages/server/src/routes.ts:82` adds `Project.sweepNode`; `packages/core/src/project.ts:521-532` runs `project.sweep()` immediately and then repeats it once an hour. `sweep` itself (`project.ts:461-509`) selects every idle project and all worktree rows (`:473-484`) and calls `fs.exists` once per idle project (`:486-490`, `:495`).
- Cost scenario: every standalone boot queries the project and worktree tables and stats the canonical directory of every project idle for an hour. On a developer database with many projects or worktrees that is dozens to hundreds of filesystem calls for an hourly maintenance task that cannot affect a one-prompt run.
- Minimal safe fix: delay the first sweep by the existing `SWEEP_INTERVAL` before entering the periodic loop, so a short-lived process never sweeps and a long-lived server starts after the same one-hour delay. Archive and canonical-directory results are unchanged; they are only computed at most one interval later.
- Risk: low. A project whose directory disappeared stays listed for up to an hour after startup instead of being archived during boot. The same one-hour staleness already applies between sweeps of a running server. Tests that expect a boot-time archive need to advance the clock.

## Checked, not selected

- **Blob retention cleanup** (`packages/core/src/blob-store.ts:87-95`): the first pass runs immediately and reads the blob directory plus stats every retained file (`FileRetention.cleanup`). It is maintenance-only, but this environment has no blobs, so it was ranked below the items above. The same one-interval delay fix applies; risk is old blobs surviving up to an hour longer.
- **Video poller** (`packages/core/src/video-generation.ts:288-315`): `tick` scans the `video:` KV prefix immediately and every five seconds. The change was already rejected in unit 04 because of `TestClock` behaviour (`docs/perf-loop/LOG.md`); do not retry it without a test-first design.
- **Machines table read** (`packages/core/src/machine/machines.ts:127-141`): the layer selects every machine row at boot even though the one prompt need not use a machine. Making the row read `Effect.cached` inside the first service call would remove one query; the state is already a per-process snapshot, so results are unchanged. Small.
- **V1 migration fork** (`packages/core/src/database/v1-migration.bun.ts:512-527`): covered inside finding 3 rather than as a separate item; the probe itself is two small reads.
- **Session search build** (`packages/server/src/process.ts:136-137`, `packages/core/src/config/plugin/session-search.ts:11-18`): the fork is unconditional, but `SessionSearchBuild.run` waits for a Location to turn on `sqlite_fts` (`session/search-build.ts:91-100`). Release builds default that flag off (`packages/schema/src/config/flag.ts:27-31`), so there is no build for a normal one-prompt `latest` run. In local/dev builds it can index the whole database; that is a separate dev-only cold-start cost.
- **MCP, repository watchers and restart recovery**: MCP connections are forked after Location boot (`packages/core/src/mcp/index.ts:913-927` in unit 31's reading); `LocationWatcher` waits for plugin activation and then watches `.git/HEAD` (`packages/core/src/filesystem/location-watcher.ts:90-99`); `SessionRestart.resumeSuspendedSessions` is installed only when `lifecycle` exists, i.e. not in `--stdio` (`packages/server/src/process.ts:129-133`). None of these block a one-prompt standalone boot, so no change is proposed here.
- **Built-in plugin activation** (`packages/core/src/plugin/supervisor.ts:146-194`, `packages/core/src/plugin/internal.ts:266-335`): every Location boot runs the effects of the built-in plugins so their tools, agents, providers and config hooks are registered. Those registrations determine the first prompt's tool schema and model list, so skipping or deferring them wholesale would change results. Only the update checks (finding 4) are safely outside that path.
- **TokenEconomizer**: no such plugin or module exists in this checkout (`grep -ri TokenEconomizer packages` returns nothing), so there is no TokenEconomizer load to remove.
- **Journal replay**: durable event logs are replayed per aggregate on demand through `Bus.log` (`packages/core/src/bus.ts:161-176`), not at server or Location boot. The only boot-time history work is the V1 migration probe and the opt-in session search build above.
