## Findings

Scope: read-only. Reviewed `packages/server/src/event-feed.ts`, `packages/server/src/handlers/event.ts`, `packages/core/src/bus.ts` (`notify`, `prepareRoutes`, `publishEvent`, `subscribe`), and `packages/protocol/src/groups/event.ts` (`isOpenCodeEvent`). Already optimised, do not redo: `EventFeed.publish` encodes each event at most once for all subscribers (`event-feed.ts:50-53`), and per-subscriber type filters are precomputed into a `Set` at subscribe time (`event-feed.ts:79`). The hot production path is a burst of ephemeral stream deltas (`session.text.delta`, `session.reasoning.delta`, `session.tool.input.delta`), one bus publish and one SSE frame per token, multiplied by connected clients.

Ranked by expected cost on that path.

### 1. Per-subscriber UTF-8 encode of the same SSE frame
`packages/server/src/handlers/event.ts:32` (with `Stream.encodeText`), after `packages/server/src/event-feed.ts:29-31`.
Cost scenario: the feed already produces one `string` per event, but each subscriber's response stream runs `Stream.encodeText`, so every connected client runs `TextEncoder.encode` again over the identical frame and allocates a fresh `Uint8Array`. With N clients and delta bursts this is N encodes and N byte-array allocations per token; the JSON work is already shared, the byte work is not.
Minimal fix: encode once where the frame is produced. Have `EventFeed.publish` convert the encoded string to a `Uint8Array` and queue that shared immutable chunk instead of the string; keep `frame` returning the same `data: ...\n\n` string for the existing wire test and derive the byte chunk from it. In the handler, drop `Stream.encodeText` for the live stream and encode the per-connection `server.connected` frame and the constant heartbeat once (module-level bytes or a single `TextEncoder` call). Concatenated bytes are identical to the current `Stream.encodeText` output.
Risk: changes the `EventFeed.subscribe` element type from `string` to `Uint8Array`, so `packages/server/test/event-feed.test.ts` comparisons must be adjusted; keep the string `frame()` test. Shared `Uint8Array` chunks must not be mutated by the response layer (they are not). Order is unchanged.

### 2. `prepareRoutes` allocates two maps per single-event publish before the envelope fast path
`packages/core/src/bus.ts:229-231`, called from `bus.ts:401` (durable single publish) and `bus.ts:481` (ephemeral single publish).
Cost scenario: every single-event publish calls `prepareRoutes([event])`, which allocates a one-element array, two `Map`s (`updates`, `resolved`) and a returned closure. Ephemeral deltas are session events whose payload carries an envelope `location`, so the loop immediately hits the `if (event.location && ...) continue` branch at `bus.ts:240-243` without writing either map. This means two maps plus closure garbage per streamed token, tens of thousands per assistant response, all discarded unused.
Minimal fix: allocate `updates` and `resolved` lazily on first `set`, and return a shared no-op route when neither was created; optionally skip the `prepareRoutes` call at `bus.ts:401` and `bus.ts:481` when the event already has a `location` and is not `session.created`, `session.forked`, `session.moved` or `session.deleted`. The batched `publishAll` path (`bus.ts:578`) already amortises the allocation and needs no change.
Risk: low. The lazy route closure must still apply `sessions`/`routes` mutations for real routing events; skipping the call for envelope-located events must preserve the `session.created`/`forked`/`moved`/`deleted` exceptions. Keep `routes` (`WeakMap`) writes identical, since ordering of routing has no byte effect.

### 3. One `Effect.try`/`pipe`/`catch` graph allocated per published event just to run a synchronous render
`packages/server/src/event-feed.ts:53-64`.
Cost scenario: `render` (`frame` or the test encode) is synchronous, but each event builds `Effect.try({...})`, a `pipe`, and a `catch` closure chain even when encoding succeeds. On a delta stream this is one effect graph per token, before any subscriber work.
Minimal fix: call `render` inside a plain `try`/`catch` in the generator, assign `encoded`, and only on the catch path run the existing `Effect.logError(...)` and `fail(error)` once, then return. Encoding still happens exactly once per event and only when a subscriber matches; error semantics stay "log and fail all subscribers".
Risk: low. Must preserve the current behaviour that a render failure delivers no frame and fails every subscriber via the existing `fail` helper. `Effect.fnUntraced` generator overhead remains but is not removable without changing `Bus.Subscriber` to return a non-Effect.

### 4. Per-subscriber `Map` entry destructuring allocates an array per subscriber per event
`packages/server/src/event-feed.ts:51`.
Cost scenario: `for (const [subscriber, types] of subscribers)` allocates a map iterator and a two-element array for every subscriber on every event, so N clients times delta count arrays, only to read `types`. The `Set.has` filter itself is already cheap.
Minimal fix: iterate without entry destructuring, for example `subscribers.forEach((types, subscriber) => { ... })`, or `for (const subscriber of subscribers.keys())` followed by one `get`, or keep a parallel array of `{ queue, types }` and use an index loop. Insertion order is preserved by all three, and deleting the current entry on overflow remains safe.
Risk: none observed. `continue` must become an early `return` inside a `forEach` callback; keep the `subscribers.delete(subscriber)` plus `Queue.failCauseUnsafe` overflow branch intact.

### 5. No coalescing of per-delta socket writes; queue is sized in frames
`packages/server/src/handlers/event.ts:31-33`, `packages/server/src/event-feed.ts:8` and `:78`.
Cost scenario: every delta becomes its own response chunk, so a burst produces one write per token per client. The per-subscriber queue is 4096 frames (`SubscriberCapacity`), which bounds retention in frames but means a slow client can disconnect after 4096 queued frames; encoded frames are shared strings, so memory is not duplicated per subscriber, only the queue slots are. The dominant cost here is chunk/write overhead, not queue memory.
Minimal fix: coalesce adjacent already-encoded frames before they reach the response, for example `Stream.groupedWithin(64, "1 millis")` on the merged output followed by joining the strings into one chunk. This concatenates the exact same frame bytes in the same order and does not merge event payloads, so the wire bytes are byte-identical; it only changes chunk boundaries. Keep the frame queue capacity as is; lowering it would trade write batching for an earlier disconnect threshold with no clear win.
Risk: adds up to the grouping window of latency per flush and needs verification that heartbeat chunks merged before grouping (`handlers/event.ts:30`) are not delayed in a way existing stream tests reject. Any test that asserts one chunk per published event must be checked. Do not coalesce at the event level (merging deltas) because that changes the JSON bytes and breaks ordering assumptions.
