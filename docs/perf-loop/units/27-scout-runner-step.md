## Findings

Scope read: `packages/core/src/session/runner/{step.ts,llm.ts,publish-llm-event.ts,to-llm-message.ts}`, `packages/core/src/session/history.ts`, `packages/core/src/session/projector.ts`, plus the ephemeral-event definitions in `packages/schema/src/session-event.ts`. No overlap intended with units 14 (history cache), 15 (retry/cwd/prepared spread), 25 (fanout yield), the message-updater matcher rewrite, or inbox prepared statements.

1. Per delta: every stream fragment is buffered twice, and each batch re-flattens the whole unpublished prefix.
   `packages/core/src/session/runner/publish-llm-event.ts:198-235`. `append` does both `current.values.push(value)` (:201) and `current.pending += value` (:202); `publishDelta` (:187-197) hands the accumulated `pending` to the bus and resets it, and `end` joins every chunk again with `current.values.join("")` (:229). So the accumulator adds a second representation of the block plus one cons node per delta, and every 100 ms batch allocates a flat copy of the entire not-yet-published prefix (a 100 KB reasoning block in ~10 byte deltas flattens tens of KB per tick until it is drained). `values` cannot simply be dropped: `TextEnd.text`/`ReasoningEnd.text` are optional (`packages/ai/src/schema/events.ts:173-180,197-204`), so `flush()` on a cut block needs the accumulated text. Minimal fix: replace `pending: string` with `pendingFrom: number`; start the timer when `pendingFrom < values.length`; `publishDelta` publishes `values.slice(pendingFrom).join("")` and then sets `pendingFrom = values.length`; keep `end`'s `value ?? current.values.join("")`. Published delta strings and the final text are byte-identical (same chunk sequence), and one full copy of the block disappears. Risk: low.

2. Per delta: `record()` allocates a `StepRecord` and scans the tool map on every provider event.
   `packages/core/src/session/runner/step.ts:139,143` calls `publisher.record()` once per streamed event (twice on the first output event); `packages/core/src/session/runner/publish-llm-event.ts:615-624` builds an object and runs `Iterable.some(tools.values(), ...)`. The scan short-circuits at the first settled local call, but a step whose calls are all provider-executed (`providerExecuted: true`, e.g. hosted search) never matches, so D deltas × K hosted calls iterations, plus one allocation per delta. Scenario: a hosted-tool step with 20 calls and 20k deltas pays ~400k predicate calls and 20k objects for data that only changes at tool boundaries. Minimal fix: maintain a `needsContinuation` boolean at the mutation points (`tool.called` :500, `tool.settled` in `tool-result` :524 and `toolExecution` :589 / `failTool` :371), so `record()` stays O(1), and read `providerFailed`/`outputStarted` as primitives for the two hot checks in `step.ts` instead of materializing a record. Risk: low, provided every site that flips `called`, `settled` or `providerExecuted` updates the flag; the final `needsContinuation` decision at :328 must stay exact.

3. Per step: the prompt is converted and token-estimated twice (three times when compaction is due).
   `packages/core/src/session/runner/llm.ts:258` calls `SessionCompaction.estimatePrompt(loaded)` and `llm.ts:267` calls `SessionModelRequest.baseTranscript` over all messages. `estimatePrompt` independently rebuilds the transcript from the last measured assistant onward (`packages/core/src/session/compaction.ts:1118-1141` → `transcript` → `baseTranscript` at :991-998) and re-estimates system, tools (`JSON.stringify` of every tool schema, :1229) and every part. When auto-compaction is due, `compact` calls `measuredPrompt` → `estimatePrompt` a third time (`compaction.ts:483`, `:1186-1195`). The code already notes the duplication (`compaction.ts:1122-1124` TODO). Scenario: a 40-step turn reconverts the whole transcript once per step in the runner and reconverts the post-anchor tail plus the full tool/system estimate again per step, so per-step cost grows with history and tool-definition size rather than with the new output. Minimal fix: build the transcript once in `runStep` and pass it (or its `Estimate`) into `compaction.compact`/`precompute`/`measuredPrompt`, so the anchor estimate reuses the runner-shaped request; at minimum return the already-computed `estimate` into `measuredPrompt` when the measured model/variant/agent still match. Risk: medium — `estimatePrompt` slices from the anchor and applies `boundImages`/`unsupportedParts` differently, so the reused shape must produce exactly the same token totals or compaction will trigger at a different point.

4. Per step: quadratic look-ahead when replaying a cut assistant message.
   `packages/core/src/session/runner/to-llm-message.ts:183-189` runs inside the `flatMap` at :172: for each reasoning item of a cut message (`message.error !== undefined || message.finish === undefined`) it allocates `items.slice(index + 1)` and scans every later item with `some(...)`. That is O(n²) element copies plus one array allocation per reasoning item, repeated on every step because each step reloads and reconverts history. Scenario: an assistant aborted by Esc after a few hundred text/tool blocks makes every following step pay tens of thousands of slice copies for no new information. Minimal fix: before the `flatMap`, compute `const lastContinuation = items.findLastIndex((item) => item.type === "tool" || (item.type === "text" && item.text.trim() !== ""))` and drop the reasoning item when `cut && index > lastContinuation`. Same predicate, O(n) once. Risk: low; output order and content are unchanged.

5. Per step: two full worktree snapshots per step, even when the step ran no tool.
   `packages/core/src/session/runner/step.ts:80` forks `snapshots.capture()` for every attempt and `step.ts:291-300` joins it and captures a second tree on every step that recorded a finish or failure, then calls `snapshots.files` for the diff. Snapshots are enabled by default for git locations (`packages/core/src/snapshot.ts:82,119`) and each capture runs `git.tree.capture` over the scoped worktree plus periodic `objects.pack` (`snapshot.ts:133-147`). Scenario: a pure text answer with no tool calls still performs two full worktree captures per step; on a large repository that filesystem/git walk dominates step latency and writes throwaway git objects. Minimal fix: when `toolRuns` is empty and the step recorded a finish, reuse `pendingStartSnapshot` as the terminal `snapshot` and skip the second `capture`/`files` call (equal IDs already yield `files: []` at :294-296); keep the current path whenever any tool ran. Risk: medium — a plugin hook or a concurrent writer can change files during a text-only step and would no longer be attributed to it (`Step.Ended.snapshot` would be the start tree).

Projector delta path (negative result): there is no per-delta DB cost to remove. `session.text.delta`, `session.reasoning.delta` and `session.tool.input.delta` are `Event.ephemeral` (`packages/schema/src/session-event.ts:419-428,458-467,502-509`), and `publishEvent` only resolves routes and notifies for non-durable events (`packages/core/src/bus.ts:480-484`). The projector registers only `Text.Started`/`Text.Ended` for text (`packages/core/src/session/projector.ts:1200-1201`; reasoning and tool-input follow the same pattern), so deltas never reach `updateAssistantPart`. The per-block `Ended` write (`projector.ts:763-853`: SELECT join + decode + `produce` + encode + UPDATE) is a per-boundary cost already covered by units 22 and 26, not repeated here.
